# Идеи следующего этапа

Приоритет остаётся прежним: простая поддержка, один бинарник, минимум внешних
сервисов и никаких скрытых изменений.

В 1.2 закрыты два прежних практических пробела: key-only onboarding нового
пользователя с другого ПК и подтверждённый сброс только bastionctl-owned
политики без затрагивания пользовательских файлов.

## Наиболее полезные

1. **Планировщик без daemon на сервере.** Генерация готовой задачи для
   `systemd --user`, cron или Windows Task Scheduler на ПК администратора:
   периодический `fleet audit-all`, локальный отчёт и ненулевой exit code.
2. **Уведомления только о новом.** Опциональный local command hook для новых
   critical/high findings и drift. Секреты мессенджеров остаются вне
   `bastionctl`; hook получает минимальный JSON через stdin.
3. **Двухфазная ротация и отзыв SSH-ключей.** Добавить новый ключ, проверить отдельное
   соединение именно им, сохранить recovery window и только отдельной командой
   удалить старый. Для пользователей, созданных в 1.2, показывать fingerprints
   и отзывать только выбранную строку, никогда не удаляя аккаунт/home.
4. **Доказательство восстановления backup.** Кроме freshness marker хранить
   подписанный receipt последнего тестового restore: время, backup ID,
   проверенные объекты и оператор — без содержимого данных.
5. **Подписанный release manifest и self-update.** Проверка embedded public key,
   SHA-256, временный self-test и атомарная замена. Обновление только по явной
   команде, с сохранением предыдущего бинарника.

## Затем

6. **Advisory inventory.** Сопоставлять установленные пакеты с подписанным
   offline feed безопасности Debian/Ubuntu и показывать только применимые
   уязвимости; сетевой поиск не должен влиять на `apply`.
7. **Hash-chain истории.** Связать локальные отчёты хешами и экспортировать
   подписанный audit bundle для внешнего backup.
8. **Проверки TLS и приложений как read-only plugins.** Сертификаты, security
   headers, reverse proxy, database bind/listen — без автоматической правки
   неизвестной конфигурации приложения.
9. **Provider checks.** Только read-only проверка rescue, snapshots, MFA и
   cloud firewall через явно подключаемые адаптеры; credentials не сохранять в
   реестре.
10. **Политики для ролей.** Версионированный policy bundle с review diff перед
    раскаткой на группу серверов и поэтапным canary apply; стандартный
    пользователь и sudo-администратор 1.2 остаются минимальной основой.

## Осознанно отложено

- постоянный сетевой agent/controller;
- собственный SSH-протокол или хранение паролей;
- web-панель и отдельная база данных;
- автоматическое удаление пользователей, firewall-правил или пакетов;
- автоматическая правка Docker/nftables без описанной сетевой архитектуры.

Эти функции заметно увеличивают поверхность атаки и стоимость сопровождения.
Их стоит добавлять только после реальных сценариев, которые не покрываются
текущей SSH-моделью.
