# bastionctl 2.1

`bastionctl` — настольное приложение для администратора Windows, которое
подключается к Ubuntu по SSH, показывает состояние защиты и безопасно управляет
настройками сервера. Для администратора распространяется один `bastionctl.exe`:
Ubuntu-компоненты amd64/arm64 уже находятся внутри. Серверная часть не является
daemon — она запускается только через SSH и ограниченные правила `sudoers`.

Текущая целевая пара платформ:

| Роль | Поддерживается в 2.1 |
|---|---|
| ПК администратора | Windows 10/11 x64, WebView2 |
| Сервер | Ubuntu Server 22.04/24.04 LTS, amd64 или arm64 |
| Будущие цели | Windows arm64, macOS/Linux admin, Debian server |

Проект не использует Python, не содержит телеметрии и не открывает собственный
сетевой порт на сервере.

## Интерфейс

Windows-приложение построено на стабильном Wails 2 и системном WebView2. В нём
есть:

- список нескольких серверов с состоянием и последней проверкой;
- безопасный первый вход по IP и одноразовому SSH-паролю;
- отдельная сверка и закрепление fingerprint для каждого сервера;
- встроенная SSH-консоль с настоящим Ubuntu PTY, изменением размера, `sudo`,
  `passwd` и полноэкранными терминальными программами;
- автоматический выбор и установка встроенного Ubuntu-компонента с SHA-256,
  точным подтверждением, backup и откатом;
- `audit → plan → apply`, история отчётов и точные подтверждения опасных
  действий;
- профили `minimal`, `web`, `docker-host`, `wireguard`, `database` и редактор
  основных параметров SSH, UFW, Fail2ban, обновлений и backup markers;
- создание key-only SSH-пользователя для входа с другого ПК;
- подписанные snapshots и drift-контроль;
- безопасный сброс только политики bastionctl без удаления пользователей,
  домашних каталогов, `authorized_keys`, приложений и их данных;
- мастер VLESS + TLS + XHTTP с закреплённым 3x-ui, автоматической серверной
  частью и отдельной инструкцией ручных действий.

Основной SSH-транспорт встроен в приложение и использует поддерживаемые
алгоритмы `golang.org/x/crypto/ssh`. Для записей, которые намеренно используют
SSH agent без файла ключа, приложение сохраняет совместимый fallback на
Windows OpenSSH Client.

## Первый запуск

Скачайте один файл и откройте его двойным кликом:

```text
bastionctl.exe
```

Ничего распаковывать и класть рядом не нужно. Приложение само определяет
`amd64`/`arm64`, но не загружает компонент до показа плана и точного
подтверждения `INSTALL <server-id>`.

Если WebView2 отсутствует, установите официальный Microsoft WebView2 Runtime.
В актуальных Windows 10/11 он обычно уже установлен.

Текущая сборка пока не подписана коммерческим Windows-сертификатом. Если
SmartScreen показывает предупреждение, сначала проверьте SHA-256 по
`SHA256SUMS`, затем используйте «Подробнее» → «Выполнить в любом случае».

### Новый VPS: вход по IP и паролю

1. Нажмите «Добавить сервер».
2. Укажите IP, SSH-порт, пользователя первого входа (`root` для нового VPS) и
   включите «Первый вход по паролю».
3. Оставьте постоянного администратора `bastion` или задайте своё имя.
4. В панели VPS откройте rescue/serial console и независимо получите
   fingerprint:

   ```bash
   ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
   ```

5. В приложении нажмите «Сверить fingerprint», сравните значения и введите
   точную строку `TRUST SHA256:...`.
6. Откройте «Первый вход» и введите выданный провайдером пароль. Если вход
   выполняется от `root`, в том же встроенном терминале задайте sudo-пароль
   новому непривилегированному администратору.
7. Приложение установит публичный Ed25519-ключ, выполнит отдельный проверочный
   вход новым ключом и только после этого отключит bootstrap-состояние.
8. Нажмите «Установить». Приложение read-only проверит Ubuntu и архитектуру,
   покажет встроенный файл, размер, SHA-256 и пути назначения. Введите
   `INSTALL <server-id>`; только после этого начнётся загрузка.
9. Ubuntu запросит sudo-пароль во встроенной консоли. Установка проверит число
   байт, SHA-256, `visudo` и совпадение версий, а при ошибке попытается вернуть
   прежние управляемые файлы.

Пароль и passphrase существуют только в памяти активного SSH-подключения. Они
не записываются в реестр, конфигурацию, отчёты или историю консоли. Закрытие
сессии освобождает связанные учётные данные. Sudo-пароль вводится прямо в
удалённый PTY с отключённым echo.

Если host key изменился, приложение блокирует вход. Заменить закреплённый ключ
можно только после независимой проверки и точного подтверждения
`REPLACE SHA256:...`; предыдущая запись сохраняется рядом как
`known_hosts.previous`.

### Уже настроенный ключ

При добавлении укажите `user@host` и путь к закрытому ключу, отключив парольный
bootstrap. Пользователь `root` не допускается как постоянная учётная запись.
Для зашифрованного ключа passphrase вводится в соответствующем поле операции и
не сохраняется.

## Безопасное применение политики

Перед первым `apply` должны быть доступны:

1. текущая SSH-консоль и проверенный второй вход;
2. rescue/serial console провайдера;
3. актуальная резервная копия и понятный процесс восстановления;
4. корректный CIDR административного IP;
5. внешние firewall-правила провайдера для действительно нужных портов.

Рабочий порядок в приложении:

1. «Аудит» — только чтение;
2. «План» — точный список изменений;
3. `APPLY <server-id>` — явное применение;
4. повторный аудит и проверка входа во второй сессии;
5. snapshot для нового baseline.

SSH меняется только после проверки пользователя, ключа, прав и `sudo`.
Конфигурация проходит `sshd -t`/`sshd -T`; UFW применяется последним, причём
allow фактического SSH-порта создаётся до `default deny incoming`.

Сброс также разделён на план и `RESET <server-id>`. Он удаляет только
управляемые drop-in и помеченные правила UFW. Не удаляются аккаунты, home,
ключи, пакеты, данные сервисов и сторонние firewall-правила. Если удаление SSH
allow может отрезать доступ, правило сохраняется с предупреждением.

## Пользователь для другого ПК

На втором ПК самостоятельно создайте Ed25519-ключ:

```bash
ssh-keygen -t ed25519 -a 64
```

В разделе «Пользователи» вставьте только содержимое файла `.pub`. Закрытый ключ
не покидает второй ПК. Sudo выдаётся отдельным переключателем; по умолчанию
создаётся обычный key-only пользователь.

## VLESS + TLS + XHTTP

В разделе «Сервисы» задаются домен, email Let's Encrypt и публичный IPv4.
Автоматическая часть:

- добавляет требования TCP 80/443 в обычную политику, но не применяет их без
  общего `plan/apply`;
- скачивает только закреплённый 3x-ui `v3.7.0` для amd64/arm64 и проверяет
  SHA-256 до распаковки;
- держит панель на `127.0.0.1`, устанавливает сертификат через системный
  Certbot и создаёт узкий SSH `PermitOpen` для локального туннеля;
- использует ownership markers, backup/rollback и отдельные
  `plan/apply/verify`.

Пользователь должен самостоятельно:

1. приобрести/выбрать домен и создать точную A-запись на IP сервера;
2. открыть TCP 80/443 в firewall панели VPS; порт панели наружу не открывать;
3. после установки прочитать временные root-only данные панели через
   встроенную консоль, открыть указанный SSH-туннель и включить 2FA;
4. в 3x-ui создать VLESS inbound: порт 443, transport XHTTP, security TLS,
   decryption none, новый UUID и пути сертификата, показанные приложением;
5. импортировать ссылку/QR в свой Xray-клиент, проверить соединение и удалить
   временный файл данных панели;
6. вернуться в bastionctl и выполнить `verify`.

Приложение не покупает домен, не меняет firewall провайдера, не хранит UUID или
пароль панели и не обещает работоспособность конкретного XHTTP-режима в любой
сети.

## Серверный CLI

Ubuntu-компонент остаётся пригодным для диагностики через rescue-консоль:

```bash
sudo /usr/local/bin/bastionctl server audit --config /etc/bastionctl/config.toml
sudo /usr/local/bin/bastionctl server plan --config /etc/bastionctl/config.toml
```

`apply` и `reset` требуют `--yes`. Для автоматизации сохранены JSON schema v1
и прежний fleet/admin CLI, но основным пользовательским интерфейсом 2.1
является Windows-приложение.

## Сборка

Требуются Go 1.25+, Node.js 24+ и npm:

```bash
npm --prefix ui/windows ci
npm --prefix ui/windows run build
CGO_ENABLED=0 go test ./...
CGO_ENABLED=0 go vet ./...
VERSION=2.1.0 sh scripts/build.sh
```

Frontend содержит только vanilla JavaScript, Vite и xterm.js. Production
assets и оба Ubuntu-компонента встраиваются в один production Windows `.exe`;
Node.js и Go на компьютере администратора не нужны. Ubuntu payload’ы собираются
статически с `CGO_ENABLED=0` непосредственно перед линковкой Windows-файла.
